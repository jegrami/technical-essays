# What Happens When You Open an App?

An app is a set of instructions, written in a programming language and then translated into a form your device's processor can carry out directly. That translated form is saved as a file on your device: a `.exe` file on Windows, a `.app` on a Mac, an `.apk` on Android. Each of these file types is built to a format the operating system recognizes on sight. 

in addition to the application's code, the file also carries a short block of information at the start describing what kind of program it is, which processor architecture it was built for, and where inside the file its code actually begins. Windows programs carry this information in a structure called PE (Portable Executable). Linux uses a format called ELF (Executable and Linkable Format). Macs use a format called Mach-O. 

Tapping an app icon or running a program from the  terminal tells the operating system (OS) to bring that program's executable file to life. The OS reads the header first to confirm the file is a program it can run. It then creates what's called a _process_, a reserved, private section of memory set aside for this running copy of the app. Within that memory, your  device's OS sets up a few distinct areas for different kinds of information. One area holds the program's actual instructions, copied in from the file. Another holds the app's data, the kind of information that exists for as long as the app runs. A third area, called the stack, keeps track of which part of the program called which other part, so that when one task finishes, the app knows exactly where to pick back up. A fourth area, the heap, is left open for the app to claim more memory as it goes, for anything it could not have known the size of in advance, like a longer list of items or a bigger file loaded on demand.

The CPU works through the program's instructions from that memory one at a time, keeping track of exactly where it is so it always knows which instruction comes next. This is the same fetch-and-execute pattern described in the article on starting up your computer, just applied to one app instead of the whole system.

Almost no app runs entirely on its own code. Most rely on shared pieces of code written by someone else. This code is called a _library_, which are chunks of pre-written functionality for stuff like showing windows, drawing text, connecting to a network, etc. For Windows, these library files usually ends in `.dll`. Macs use `.dylib` files, and Linux uses shared library files ending in `.so`. The program's header lists which of these it needs, and the OS locates and connects each one to the process before the app can rely on it.

The moment an app needs to read a file, show something on screen, or reach the internet, it asks the OS to do that on its behalf, through a request called a system call. The OS carries out the request and hands control back to the app. This back-and-forth happens constantly dozens of times a second in a typical app.

The same basic sequence (tap or click, check the file, create a process, load the code, connect any needed libraries) plays out the same way on a phone opening an app from its home screen as it does on a laptop opening a program from a start menu. The file formats and library names differ across Windows, macOS, Linux, iOS, and Android, but the underlying steps line up closely.

When you close an app, the OS reverses the setup: it takes back the memory the process was using, closes any files or network connections the app had open, and removes the process from the list of programs it's tracking. A later article looks at how your device manages to keep several of these processes running side by side without them getting in each other's way.
